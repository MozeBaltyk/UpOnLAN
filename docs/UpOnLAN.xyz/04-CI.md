## CI & release pipelines

UpOnLAN.xyz's automation lives in `.github/workflows/` (GitHub Actions) plus the local scripts under `scripts/` and `wakemeup.sh`. Together they cover two paths: a **test pipeline** (every push/PR) and a **release pipeline** that ships the container image, the menu, and the asset bundles — each independently.

### Test pipeline — `test.yml`

Triggers: every `push` and `pull_request` (plus manual `workflow_dispatch`). Four jobs run in parallel:

| Job | What it runs |
| --- | --- |
| `webapp` | the four Vitest layers — unit, integration, e2e, smoke (`npm run test:unit` … `test:smoke`) |
| `specs` | the release-flow Python suite (`./tests/specs/run.sh` — shell scripts, `release/output` layout, doc-link integrity) |
| `shell` | `bash -n` syntax over `scripts/*.sh`, `src/*.sh`, `wakemeup.sh` |
| `container` | `docker build` of the Containerfile (build-only smoke, nothing pushed) |

### Release pipeline — local (one-shot)

For a single host, `scripts/build_release.sh <version>` runs the whole thing in enforced order (ROMs → assets → menu), and `wakemeup.sh` wraps the day-to-day actions:

| Command | What it does |
| --- | --- |
| `./wakemeup.sh -a build` | build the container image |
| `./wakemeup.sh -a mirror-assets` | build the asset layer (`release_assets.sh`) |
| `./scripts/build_release.sh <version>` | ROMs + assets + menu, in order |
| `./wakemeup.sh -a deploy --local` | serve `release/output` and deploy the local manifest |
| `./wakemeup.sh -a test-webapp` | run the webapp test suite in the container |

See [Deployment](UpOnLAN.xyz/02-Deployment.md) for the full local flow.

### Release pipeline — GitHub (three workflows)

Three independent `workflow_dispatch` jobs, each shipping one artifact on its own schedule (a menu fix does not force a multi-GB asset rebuild):

| Workflow | Produces | Destination |
| --- | --- | --- |
| `image.yml` | the webapp container | `ghcr.io/mozebaltyk/uponlan:<version>` + `latest` |
| `release.yml` | the menu tarball | GitHub Release tag `<version>`, asset `menus.tar.gz` |
| `assets.yml` | asset bundles | one GitHub release per bundle (tag = `<key>`) + an `assets` tag carrying `endpoints.yml` |

`<version>` comes from `src/webapp/package.json`; `<key>` is the endpoint key `${OS}-${VERSION}-${GENERIC_ARCH}` produced by `release/assets/build.sh` (e.g. `proxmox-ve-8.4-1-x86_64`).

- **`release.yml` (menu)** — checks out `main`, reads the version, fails if that git tag already exists, installs the iPXE toolchain, builds the ROMs (`build_ipxe_roms.sh`), packs `release_menu.sh <version>`, extracts release notes, and uploads `menus.tar.gz` as the `<version>` release asset.
- **`assets.yml`** — installs `yq` + `p7zip-full`, runs `MIRROR_LAYOUT=github scripts/release_assets.sh`, then for each bundle `gh release create <key> --prerelease` (or `gh release upload --clobber` on a re-run), and finally publishes `endpoints.yml` on the `assets` tag.
- **`image.yml`** — reads the version, logs in to GHCR, and `docker build-push-action` tags the image `<version>` and `latest`.

### Conventions that keep the releases from colliding

Menu tags (`0.0.2`) and asset tags (`proxmox-ve-8.4-1-x86_64`) share the same GitHub releases namespace, so two conventions keep them apart:

1. **Asset releases are `--prerelease`.** GitHub's `releases/latest` (used by `init.sh` to resolve `MENU_VERSION` and by the dashboard's *remote menu version*) skips prereleases, so it stays pinned to the menu release even after asset bundles are published.
2. **Menu versions are bare semver.** `fetchDevReleases` filters the release list to `^v?\d+\.\d+\.\d+$`, so asset tags never surface as "menu versions" in the endpoint browser.

### How a deployment consumes the output

`init.sh` switches on whether `ENDPOINT_URL` is a GitHub URL:

| Endpoint | Menu tarball | Asset catalog |
| --- | --- | --- |
| GitHub | `…/releases/download/<version>/menus.tar.gz` | `…/releases/download/assets/endpoints.yml` |
| Local mirror | `…/menu/<version>/menus.tar.gz` | `…/assets/endpoints.yml` |

See [Deployment](UpOnLAN.xyz/02-Deployment.md) for the deploy side and [Development](UpOnLAN.xyz/01-Development.md) for how the specs validate the pipeline.
